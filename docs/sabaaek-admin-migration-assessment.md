# تقييم إدارة سبائك الفخامة قبل نقل المصادقة

## القرار الحالي

لا تُنقل إدارة Owner وManager إلى D1 أو Better Auth في هذه المرحلة. الإدارة الحالية في Supabase تملك ضوابط server-side مثبتة، وقد تم الآن تصدير قاعدة الإنتاج واستعادة نسخة موثقة إلى `sabaaek_gold_staging` مستقلة. لذلك أصبح staging جاهزاً لتجربة إدارة جديدة، لكن لا يوجد حتى الآن أي نقل للمستخدمين أو الصلاحيات ولا أي تغيير في الإنتاج.

## ضوابط مثبتة في المصدر الحالي

دالة `sabaaek-admin` تتحقق من Bearer token عبر Supabase Auth، ثم تقرأ الدور والحالة من `profiles`. الوصول الإداري يتطلب حساباً نشطاً بدور `owner` أو `manager`، ويتطلب المالك للعمليات الحساسة مثل إعدادات الموقع وسجل التدقيق وإنشاء أو تعطيل مدير. تعديلات الأسعار تمر عبر RPC محمي في PostgreSQL، والسياسات تمنع القراءة والكتابة المباشرة لجداول الأسعار والدعوات والسجل من anon وauthenticated. كما تُسجل تغييرات الأسعار وكلمات المرور والإعدادات والمديرين في audit log.

توجد أيضاً قيود تحقق على العيارات الثلاثة، نطاق التعديل، كلمات المرور، الثيمات، وروابط التواصل. هذه الضوابط لا تعتمد على إخفاء عناصر الواجهة، وهو أمر صحيح أمنياً.

## نقاط يجب عدم إغفالها في أي نقل

يجب أن يبقى التحقق من الدور على الخادم، وأن تكون الجلسات HttpOnly وSecure وSameSite، مع إبطال الجلسة وتغيير كلمة المرور وتحديد المحاولات وسجل تدقيق. لا يجوز تخزين كلمات المرور أو صلاحيات Owner/Manager في JavaScript أو localStorage أو KV. لا يكفي Turnstile أو Cloudflare Access وحده؛ كلاهما طبقة إضافية ولا يستبدل التفويض داخل API.

يجب تحديث قائمة CORS عند إضافة نطاق staging أو نطاق إنتاج جديد، مع إبقاء allowlist صريحة لا wildcard. كما يجب عدم اعتبار عنوان البريد وحده بديلاً عن role profile، وعدم نقل سجلات الإدارة قبل مطابقة عدد الصفوف والقيود والصلاحيات.

## خيار إدارة staging الحالي وخيار Better Auth + D1

تمت إضافة جداول staging منفصلة `site_settings` و`price_adjustments` بقراءة عامة server-side من العامل المرحلي، مع قيود تمنع عيارات غير 24/21/18 أو تعديلات خارج نطاق -5000 إلى 5000 ريال. لا توجد في العامل المرحلي مسارات POST أو PUT أو DELETE، ولا يعتمد public config بعد الآن على Supabase.

Better Auth مرشح للاختبار في Worker مستقل لأنه يملك تكاملاً موثقاً مع D1. لكنه ليس ترحيلاً تلقائياً للإدارة الحالية: يجب تصميم جلسات وأدوار وسجل تدقيق وقواعد rate limiting والاستعادة، ثم اختبار رفض كل عملية Owner من Manager على الخادم. يستخدم KV، إن لزم، للكاش غير الحساس فقط. نقل المصادقة لا يبدأ قبل اعتماد مخطط الجلسات وعمليات password change وaudit والاختبارات السلبية.

## شرط البدء

قبل أي نقل مصادقة: الحصول على صلاحية D1 مقيدة للحساب الصحيح، تصدير قاعدة سبائك، استعادة نسخة إلى قاعدة staging منفصلة، مقارنة schema والصفوف، ثم اختبارات API مستقلة لحالات unauthenticated وmanager وowner وinactive وexpired session وpassword change required.

## نتيجة المرحلة

تم تجاوز شرط النسخة: استُعيدت 470 استعلاماً بنجاح إلى D1 staging، وتطابقت جداول التاريخ الأربع مع 433 نقطة و14 تجميعاً يومياً و14 شهرياً و1 آخر سعر. أضيفت طبقة public config محلية، ونُشر العامل المرحلي، ونجحت 17/17 من اختبارات العقود المختارة. لا تغيير في Supabase أو الإنتاج، ولا نقل للمستخدمين أو كلمات المرور، ولا إنشاء صلاحيات جديدة.
